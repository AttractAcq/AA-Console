# Coordinated campaign planner contract audit — 18 November 2026

**Scope:** Source at draft PR #363, after migration 569. No hosted mutation or provider action was performed. This is a source finding and a proposed correction, not a claim that a client campaign failed live.

## Reproducible contract break

1. Migration 302 permits a commercial campaign with `acquisition_mode='both'`, `runs_organic=true`, `runs_paid=true` and a Meta or Google paid platform. Later route planning and work-item migrations use separate organic and paid route packages.
2. `runCampaignPlanJob` treats `both` as v6 and calls `capture_campaign_intelligence_snapshot_v6` before asking the model to plan. The function from migration 207 rejects any mode outside `('organic','paid')`. Its immutable snapshot table has two checks that also reject `both`. A new coordinated campaign therefore cannot finish this path.
3. On plan save or crash recovery the same worker calls `create_campaign_manifest_v6`. The function from migration 205 rejects `both`; its immutable manifest table has two checks that also reject it. Merely allowing the value in the table would still leave the manifest with one `distribution` item and one module, so it cannot express both route obligations.
4. `request_campaign_action_approval_v6` from migration 206 accepts paid-build actions only for mode `paid` and organic publish only for mode `organic`. The `campaign_route_actions` and `campaign_launch_due` views from migration 245 resolve one distribution route and classify `both` as not live even when evidence exists.
5. The legacy paid build paths still gate on `acquisition_mode='paid'` (migrations 239, 243, 260, 292 and 294). The newer Meta manual operator source (migration 539) instead checks `runs_paid`, selects the paid route from an approved preparation package and includes only paid output references. That route-aware manual source is distinct from automated ad execution. The Google manual sheet and bundle (migrations 243, 260 and 541) remain paid-only and do not bind an exact paid route package.

## Correction contract for review

- Extend the snapshot and manifest constraints and writers to accept `both` only with an explicit Meta or Google paid platform. Preserve existing immutable rows and job-key retry semantics.
- Keep one commercial manifest, but give a `both` manifest separate `distribution` (organic) and `paid_distribution` items. Require each through its own route and action; preserve the old item keys and outputs for single-route manifests. The attribution item must depend on both distribution items for `both`.
- Allow organic publication and the selected paid-build action against a `both` manifest as separate exact approvals. Do not treat one approval as authority for the other route.
- Expand route-action readiness to show both obligations. For a `both` campaign, the legacy `live` boolean should be true only after both a post and paid spend are observed, with a distinct partial-live verdict when only one route has evidence. Missing paid account binding or metric coverage must remain unknown rather than zero.
- Verify a rollback-only fixture with a `both` campaign from job-bound Intelligence capture through an idempotent manifest, two distribution requirements, separate exact action approvals, and readiness/live states. Include wrong platform, stale package, cross-client and single-route regressions.
- Review each Meta and Google paid handoff against the paid route package, and the organic scheduler against the organic package. Keep execution held where an exact route binding or provider receipt is absent.

**Candidate source correction:** Migrations 570–571 now widen the immutable Intelligence snapshot and manifest, give a `both` manifest separate organic and paid distribution requirements, accept separately scoped approval requests, and distinguish partial from full recorded live state. The rollback fixture checks job/client binding, idempotency, route split, wrong platform, stale manifest and single-route preservation. A local post/spend fixture tests the view's decision rule; it is not a provider receipt or read-back.

**Remaining Google production break:** The planner and immutable content spec allow `paid/google_ads/text/single`. `runCampaignSweepJob` explicitly refuses every `google_ads` piece before composing its workflow. This is a real producer gap: `SweepPiece.platform` and the idea/brief `target_platform` use the social `post_platform` enum, and the ideation worker requires a supported post destination. The preparation readiness function requires each planned piece to have a QA-passed sweep output. Therefore a coordinated Google campaign cannot obtain a complete reviewed preparation package simply by accepting `both` in the Google sheet and bundle. A correct fix must define how Google search copy is produced and reviewed as paid-route work, keep its exact paid route package, and connect it to the manual operator bundle. Do not silently drop planned Google pieces, count a manual sheet as produced creative, or release an automated Google build. The Meta manual bundle's existing route selection does not prove live ad-account handoff or activation.

The `post_platform` enum also types scheduled social posts and daily content settings. Adding `google_ads` to that shared enum would make it look like a schedulable social destination and still would not produce Google-specific headline/description lengths. Keep Google search copy as a distinct paid-route artifact or introduce a separate content-destination type with explicit scheduling guards. The reviewed output must carry its source idea, offer and paid route version; include bounded copy and claim QA; enter the same human approval gate; and be referenced by the Google manual bundle hash. The bundle remains an operator handoff, with activation, spend, provider ID and read-back recorded separately.

Migration 260's `google_ads_copy` table already constrains the 3–15 headlines and 2–4 descriptions, but it is one mutable row per campaign and is used by the held automated-build prerequisite. It does not carry a content-spec piece, sweep work item, paid route package or immutable reviewed version. The new producer should version its own output rather than overwriting that row or treating an existing `google_ads_copy` row as QA-passed campaign work. The runtime now has a pure strict-output validator in `agents/google_search_copy/contract.ts`; it is not yet connected to a worker or approval and must not be presented as generated content.

No migration is authorized for staging or production by this audit. Phase 4 and Phase 9 remain open.
