# Archived returning lead review — 19 November 2026

**Scope:** Draft PR #363, candidate migrations 638–645. Source and local rehearsal only. Neither hosted project nor any outward switch changed. The cash-positive Archive guard remains in place.

## Gap and candidate behavior

The earlier `capture_lead_v6` deduplicated against active `client_leads` only. A consented submission with the same contact as an archived lead therefore created a second active lead without an explicit decision. That split the contact's historical source, consent and outcome path.

Migration 638 retains the new consented submission as `received`, with its exact endpoint source snapshot, route, click/UTM and a same-client durable archived-lead candidate. It does not create or reopen a lead. Older archived JSON without a stored generated dedupe key is matched from the archived email/phone using the current dedupe rule. Contact-level advisory and active-row locks serialize capture with a concurrent archive. The public route still gives the same generic success response as a new or merged capture; its internal log names the review hold without recording contact details.

Migration 639 gives a signed-in client lead manager an exact packet with a source hash and two AAL2 choices: recover the archived identity or start a separate active lead while keeping the archive. The operator records a reason. The database checks that the submission and archived snapshot still match the packet, refuses multiple matching archives or a concurrent active contact, and saves an immutable decision with the resulting identity in the same transaction as promotion. The Sales OS Capture page shows held submissions and this review form. Migration 640 blocks direct archive recovery while an unresolved return is held. Migration 641 freezes held consent/source fields and refuses direct status promotion without the matching AAL2 resolution.

Migration 642 keeps a new inbound Meta DM from an archived identity as an inbound message in a closed conversation. It retains the historical identity link and refuses automatic reopening or reply. This is a holding path; it does not yet create a canonical lead-return review packet for DMs.

Migration 643 strengthens the existing durable sales-agent lead link with same-client scope and a guard on new operational links. A new conversation with the same active contact joins the active lead; a new conversation matching an archived contact remains visible with an archived candidate and no active lead. Sales OS marks that conversation as awaiting identity review. This is a holding path; its AAL2 resolution workflow is still open.

Migration 644 freezes the match-time contact, agent/page source, outcome and transcript digest in the held sales conversation. Later turns can change current contact fields without silently rewriting the reviewed match. A direct candidate rewrite or lead promotion remains held; an exact AAL2 resolution route is still needed.

Migration 645 supplies that route for one unambiguous sales conversation: a signed-in AAL2 reviewer chooses recovery or a separate lead against a hash of the frozen match, current conversation and archived row. It stores the immutable decision in the same transaction as promotion. A direct Archive recovery remains blocked while a sales return is pending, and a concurrent held form or second sales conversation for the same archived contact requires coordinated review. Sales OS shows the exact packet and requires a reason before recording the decision.

## Remaining gates

Two or more held submissions for one archived identity currently remain held rather than letting one decision silently dispose of the others. Multiple archived identities with the same dedupe key are also refused at decision time. Cross-channel or multiple sales-agent returns require a reviewed batch or manual reconciliation path. Form and sales decisions remain source-specific; they are not yet represented as canonical Unified Inbox approval classes. Archived DM messages are retained but their manual identity-resolution workflow is not built. Signed-in AAL2 usability, provider-backed capture, hosted parity and the organic/paid route-to-cash journeys remain unverified. This candidate does not accept Phases 8 or 9.
