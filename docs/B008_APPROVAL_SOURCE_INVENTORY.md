# B008 approval source, decision and executor inventory

This is the implementation inventory for a single exact-version Approval Inbox. It records **existing owners**, not a new authority model. A canonical Inbox card must mirror the owning decision and never turn an internal review into permission for an external effect. A decision stays with its existing RPC and authority check. B008 adds a second, human AAL2 gate and an append-only cross-source record; B010 will make every external executor recheck that record immediately before a write.

## Required invariants and implementation slices

1. **Canonical request identity.** `(source_system, source_kind, source_id, source_version)` identifies one frozen candidate. The canonical request stores client/global scope, type, exact artifact hash and preview, destination/account/budget, rights/consent lineage, expiry, owner role and source snapshot. If preview or lineage cannot be proven, the card is visible but decision disabled with an explicit blocker.
2. **Append-only decision events.** Store human user ID, AAL, owning source transition, reason and timestamp. RLS grants scoped reads; authenticated users never write directly. A request or decision is never updated or deleted. Revocation is another event, not a rewrite of history.
3. **Transactional source adapter.** Each owning request RPC or transition writes its canonical card in the same database transaction. Existing pending rows are backfilled idempotently with `incomplete_preview` unless exact bytes and destination can be established. A source cannot become pending without a card once its adapter is installed.
4. **Authority remains local.** Inbox decisions call the owning RPC; that RPC still checks its role, client and latest version. B008 adds `auth.role()='authenticated'`, `auth.uid()` and `auth.jwt()->>'aal'='aal2'`; Bot and service role cannot decide. Engine slot and ordinary media must remain separate owners.
5. **Execution remains local.** The executor checks the canonical decision *and* its existing approval, current rights/consent, exact artifact/destination/account/budget and switches at the last possible moment. No display-only card grants execution. External effects remain off until this check and B010 are verified.
6. **One interface.** Replace the three `approval-inbox` tabs with a unified list, exact preview, owner, blocker, source, decision history and filter. Keep deep links to the owning page for context. A card with missing preview cannot show an Approve button.

- B005 owns migrations 264–269, B004 owns 270–271, and an independent client-onboarding RLS fix has reserved 272. B008 starts at 273 only after upstream ancestry settles.
- B005 migration 267 added a distinct sales-entitlement approval class; the controlled B004 invitation adds another. The inventory now has **34** classes. The sales access switch stays off until its canonical Inbox binding and activation are independently verified.
- Gateway is a separate SQLite authority. It must not be counted in Supabase coverage until the bridge and fail-closed attestation are running.
- `campaign_action_approvals` contains nine action keys but several current UI paths bypass that class entirely. A single list without the source adapters and executor rechecks would create a false sense of coverage.

### Media and video exact-byte gap

`client_media_assets.storage_path` and `render_path` are database strings, not a hash of the media bytes. Multiple agent upload paths use `upsert: true`, so the same path can identify different bytes over time. `post_copy` is mutable and versioned per platform. The video signoff table records `(asset_id, role, render_path)` and upserts its row; client review requests also upsert one row and delete the prior client signoff. These paths cannot prove a human saw the precise media that will be published. Before ordinary media, Engine slot or owner/SMM/client video decisions count as exact-version Inbox approvals, a trusted media capture must SHA-256 the downloaded bytes (including each ordered frame where relevant), bind an immutable object version and all copy, reverify it in the owning decision, and recheck it immediately before publication. The owner and client seats need scoped canonical reader/decision authority, and each client re-request needs a distinct epoch. Migration 277 therefore exposes Engine cards with a blocker and no decision control.

### Campaign action preview classification observed in code

`google_ad_build` carries the complete approved JSON spec and exact Google Ads customer ID. `page_deploy` stores full rendered HTML in `campaign_page_approval_snapshots`, but that row is inserted **after** the campaign action request in the same transaction, so the registration is blocked until the snapshot is attached. `budget_change` carries the current and proposed daily amount, currency, ad-set target and multiplier, but the generic scope is not itself a frozen source snapshot; it remains blocked until its source row is attested. `meta_ad_build` currently lists creative IDs only in its hash input, not the creative bytes/copy shown to the reviewer; `proof_publish` lists placement hashes/destinations without their content; `lead_message` lists a sequence ID and step count without the exact ordered words. Those actions remain `incomplete_preview` until dedicated evidence builders freeze their complete candidates. The remaining action keys have no proven complete preview from the generic request function alone.
