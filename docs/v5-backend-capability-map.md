# v5 backend capability map and execution plan — 12 October 2026

## Purpose and boundary

The v5 North Star is one acquisition engine with two outcomes: a quality-checked daily package of one reel, one story and two static assets per active client, and a coherent launch-ready acquisition package for a new client within 24 hours of complete inputs and access. The source documents are `AA_Console_North_Star_Autonomous_Acquisition_Engine.docx` and `AA_Console_Landing_Page.html` in Alex's `v5_The_Autonomous_Acquisition_Engine` folder. Their claims describe the target, not the currently proven system.

This is a code and existing-test audit of the checkout, not a fresh production acceptance test. Existing live observations are recorded in `video-content-workflows-plan-2026-10-10.md`. Preserve the current Console UI while strengthening the functions and packaging them as outcome-level workflows. The release boundary in `AGENTS.md` applies: code, tests and reviewable PR only; merge, production migration and Railway deployment require Alex via Chief of Staff.

## Gaps that prevent the v5 outcomes

1. **No outcome-level run owner.** `start_master_run()` groups a sweep of agents by `run_id`; `engine_tick()` advances individual content slots; `provision_campaign()` creates page and sales-agent jobs. These are separate coordinators. None owns a whole client launch or daily four-asset package from input snapshot through QA, exception recovery and approval queue. MCP execution IDs are per tool request, not a root request spanning the graph. Reuse the existing job queue and records; add a persistent workflow-run/step/artefact contract and an orchestrator that invokes the existing functions idempotently.
2. **Daily planner describes posting cadence, not the promised package.** `client_engine_platforms.posts_per_week` and `client_engine_settings.format_mix` feed `plan_slots()` (`146_engine_settings.sql`, `149_plan_slots.sql`). A weighted mix cannot guarantee one reel, one story and two statics for every client-day. There is no daily package ID, approval cutoff, complete-package verdict or approved evergreen reserve selection. Add a deterministic daily package planner and queue; leave the current posting calendar as the distribution schedule.
3. **Quality gates are incomplete for video and launch.** Slot QA checks copy, banned phrases, claim figures, dimensions, duration and whether a reel has a render (`agents/qa`). It does not judge temporal visual defects, cast/product continuity, audible quality, caption placement or narrative quality. The last live generated reel failed visual acceptance despite rendering. Add versioned candidate selection, frame-and-motion QA, regeneration, audio validation and a final internal acceptance verdict before approval. `campaign_readiness()` currently counts any non-null page HTML and a built sales agent with `status = 'live'`; it does not test links/forms/routing/consent/tracking. That `live` condition also needs a v5 review: a package should be *ready for human activation* before the sales agent is activated, so launch readiness and live operation must have distinct states.
4. **Launch provisioning stops before a launch package exists.** `provision_campaign()` enqueues a landing page and sales agent, while campaign content, Meta handoff, page QA, conversion tests and measurement setup follow separate paths. Build a launch manifest from approved strategy and authenticated proof, derive the required components, run them in dependency order, test the conversion path and present one reviewable package. Preserve human control of page/agent activation and live paid budgets.
5. **Recovery is job-local, not outcome-aware.** Leases and retries recover a task; they do not yet answer whether a client-day can meet its cutoff, which approved backup to use, whether a launch is blocked on client input, or which dependent steps must be invalidated after a revision. Add deadlines, explicit blocker categories, versioned inputs/outputs and a recovery policy at the workflow-run level. Never promote a failed or unapproved substitute.
6. **Cross-domain identity and measurement are not fully joined.** Campaign artefacts, content slots, pages, agents, scheduled posts and external Meta IDs exist, but a single root outcome and its causal links are not consistently recorded. Attribution and creative iteration need that spine, plus observed/estimated/unknown labels and coverage metrics.

## Execution plan

This is backend packaging and quality work. It reuses the existing agent runners, queue, slot engine, campaign records, approvals and Console navigation. Each slice should be a reviewable PR with a focused migration/test set. The current reel continuity/caption branch should be reviewed as its own quality slice; do not silently fold unrelated v5 schema work into it.

### V5-0 — Establish contracts and a baseline

**Deliverable:** a versioned function-contract inventory and a repeatable baseline for the two promised outcomes. For each existing runner/RPC, record accepted input row, completion predicate, side effects, idempotency key, upstream evidence, retry behavior and human gate. Capture the current live results separately from code and test coverage, including the failed visual acceptance of AA-0127. Verify which global/client engine switches and integrations are enabled before any pilot; code presence is not an enabled service.

**Done when:** every step needed by the daily package and launch package has an owner and a checkable completion predicate; unknowns are explicit blockers, not inferred successes. This document's function table is the starting inventory.

### V5-1 — Add an outcome-level workflow spine

**Deliverable:** one `workflow_run` for either `daily_content_package` or `client_launch_package`, with versioned immutable input snapshot, client/campaign, requested-by/root MCP ID, deadline, state, blocker and final manifest. Persist `workflow_steps` with dependencies, linked `agent_jobs`, provider request IDs, artefact versions, retry count and completion evidence. Reconcile eligible steps through a bounded worker/tick; continue using the current lease-based `agent_jobs` as the execution queue. A step may advance only after its existing function's real output predicate is met, not merely because a job returned `ok`. Idempotency must cover both queue insertion and paid provider submission.

**State policy:** `pending → running → needs_input | needs_internal_qa | awaiting_human_approval | completed`; `blocked` and `failed` are explicit side exits. Revisions create a new version and invalidate only dependent steps. A process restart must resume from persisted state without replaying completed paid calls. The workflow stops at human approval and cannot call a bot asset-decision tool to approve itself.

**Done when:** a synthetic package survives duplicate trigger, worker restart, provider timeout and one failed step with one root trace. A paid submission with an ambiguous provider response must pause for reconciliation instead of blindly submitting again. This is the shared foundation for both operating modes, not a replacement for `engine_tick()` or `start_master_run()`.

### V5-2 — Make the generated reel worthy of the approval queue

**Deliverable:** candidate/acceptance loop around the current brief → opening still → Higgsfield clips → Claude/FFmpeg edit route. Anchor recurring cast, location, product and props across keyframes; record candidate stills/clips and their rejection reasons. Benchmark the same clean opening frame and direction on the configured Kling 2.5 Pro and available Kling 3.0 route, judging motion, identity, visual defects, brand fit, latency and actual provider charges. Select the production model from results, not the model label or the cheapest rate: creative quality is the release criterion. Add timed visual inspection across clips and the final cut, plus deterministic checks for dimensions, blank/black frames, text overflow, captions and audio stream. Use a model-led review for continuity and narrative issues; record its evidence and allow human override. Build an explicit sound policy: licensed music and/or approved narration where requested, and deliberate muted exports only when the brief calls for them.

**Version policy:** a failed candidate stays on file with its defect; a replacement does not silently overwrite an approved render. An internal verdict of `accepted` is required before the exact file enters the existing owner/SMM/client approval chain. A human rejection returns a reason to a versioned create/edit step.

**Done when:** at least one new F6 and one new F7 reel traverse the revised path, receive full-cut visual review, have readable captions and the requested sound treatment, and are accepted on creative quality by the owner/SMM. AA-0127 remains a failed benchmark, not a success count. Use newly authorized or synthetic reference assets for provider comparisons; the previously rejected private-still transfer is not an available test shortcut.

### V5-3 — Package daily production as exactly four finished assets

**Deliverable:** a deterministic client-local daily package planner with four required roles: one reel, one story, two statics. Link each role to an approved campaign or pillar, audience, offer, proof, publication slot and format. The existing `plan_slots()` owns posting windows; the new planner owns *production demand*, linking package roles to slots/jobs with a unique client/day/role key. During the pilot, configure one authority for package-managed slots so the legacy hourly tick cannot generate a second set for the same day. For the first pilot, a story may be a finished 9:16 still unless its approved brief requires video; the story media policy must be explicit in the package record. Prepare final captions, CTAs, metadata and exports before the approval cutoff.

**Recovery:** keep a rolling seven-day target of approved evergreen reserves, classified by compatible campaign/pillar/platform/format. If a scheduled asset fails, choose only a compatible preapproved reserve, or mark the package blocked and alert the manager. Never use a merely generated or internally QA-passed item as a publication substitute. Record cutoff risk and recovery actions on the root run.

**Done when:** one pilot client has seven consecutive client-days of four complete, internally QA-passed assets ready by the configured morning cutoff; the owner/SMM can review a single package; failure injection shows a valid reserve or an honest blocker. No autonomous publication occurs before the required human approval.

### V5-4 — Assemble a complete client launch package

**Deliverable:** preflight the actual client context, proof rights, offer, brand, target audience, account access and missing facts. From that frozen input, run campaign planning; provision page, sales-agent definition and organic/paid creative with existing functions; attach all results to the root campaign and workflow run. A launch package manifest lists what is required, what exists, exact versions, QA evidence, approvals and unresolved blockers. Keep work parallel where dependencies permit, but do not mark a launch ready because a page contains HTML or an agent row says `live`.

**Validation:** test page links, lead form submission, routing, consent, event capture, and the sales agent's permitted responses with realistic scenarios. Verify creative-to-page message and CTA continuity. Prepare paused Meta campaign/creative handoff where the client has access; record the handoff state separately from live paid management. Introduce `launch_ready` distinct from `live`: humans approve consequential claims and activation, then manage paid budgets and optimisation in Meta Ads Manager.

**Done when:** a new-client dry run with complete inputs produces one coherent reviewable package within the 24-hour target, with a tested conversion path, configured agent, internally accepted organic creative, paused Meta handoff and measurement checklist. Human approval of the exact package follows before activation. Missing access or proof pauses with a specific request instead of creating fabricated claims or a false ready state.

### V5-5 — Close recovery, measurement and learning

**Deliverable:** run-level deadlines, exception categories, retry/reconciliation reporting and explicit observed/estimated/unknown attribution coverage. Link campaign, creative angle, asset version, page, lead and external platform IDs. Feed measured results and human rejection reasons into campaign intelligence and the next idea selection as evidence-backed hypotheses; preserve approval boundaries for strategic changes.

**Done when:** the team can answer which packages met cutoff, why a package failed, cost and repair time per accepted asset, first-pass approval, launch-readiness elapsed time, and which commercial results are attributable versus unknown. A reported win must point to source records.

### Release and review order

1. Review the current video-quality PR separately, then create a focused workflow-spine PR (V5-0/1).
2. Ship reel quality in small PRs: candidate lineage, visual QA/revision, then sound and acceptance (V5-2). Run paid provider benchmarks only with permitted inputs and record actual output quality.
3. Add daily package planner and reserve/recovery as separate PRs (V5-3); pilot one client before broader enablement.
4. Add launch preflight/manifest, conversion checks and activation-state corrections as separate PRs (V5-4); dry-run one new client.
5. Add outcome metrics and evidence-driven iteration (V5-5) after both packages emit stable run/artefact IDs.

Each PR should include migration and RLS tests for new tables/RPCs, one restart/idempotency test for orchestration changes, and only the media/integration tests needed to prove its acceptance gate. The Phase 6 boundary applies at every release: prepare code, tests and reviewable PR; merge, production migrations and Railway deploys happen with Alex via Chief of Staff.

## Acceptance evidence required

- One daily client-day produces exactly four complete, internally QA-passed assets before cutoff; each has correct campaign/pillar/proof links, copy and final files. Simulate a provider failure and prove an approved backup is selected or a clear blocker is raised.
- A generated reel passes visual review across the entire cut, including cast continuity, captions, crop, motion and sound. Record every candidate, rejection and regeneration; do not count an MP4 alone as success.
- A new client with complete inputs reaches one reviewable launch package containing an approved campaign plan, tested page and conversion route, configured sales agent, organic assets, paused Meta creative and measurement checks. Human activation remains separate.
- Restart and duplicate-trigger tests prove no lost run and no duplicate paid provider submissions. Every blocker identifies the failed step and what action can resolve it.
- Track the v5 metrics: complete client-days, first-pass approval, repair time, launch-readiness hours, package completeness, run/recovery success, backlog age and attribution coverage.

## Implementation ledger

- **Workflow spine (PR #154):** persisted run, sealed dependency graph, queue reconciliation, accepted artefact provenance and internal QA evidence. The reconciler is opt-in with `V5_WORKFLOW_ENABLED`; it stops at `awaiting_human_approval`. It does not yet make daily or launch outcomes ready by itself.
- **Daily package planner (stacked branch):** client-local date and cutoff, exact four-role demand, frozen campaign and pillar context, dependency graph, idempotency and a derived readiness result. It requires explicit per-client enablement and refuses to run alongside the legacy engine planner. The story defaults to a still; video is configurable. This is production demand, not a publishing schedule or an accepted quality claim.
- **Open acceptance work:** internal video inspection and sound policy; approved reserve selection and manager alerting; real launch preflight, conversion testing and activation package; run-level recovery and attribution. The existing visual failure on AA-0127 remains unresolved until a new full-cut video is reviewed and accepted by owner/SMM.
- **Reserve and recovery (stacked branch):** a blocked final item may use one matching reserve only when the asset was already human-approved and has finished platform copy. The selection and source are recorded on the root run; lack of a match leaves the package blocked with an open alert. A seven-day coverage query reports reel, story and static shortfalls. Email delivery of these alerts to the assigned manager still needs a worker and live proof.
