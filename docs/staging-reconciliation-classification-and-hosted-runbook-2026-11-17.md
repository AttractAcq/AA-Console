### Evidence behind the classifications

- The 192 function ACL differences are semantic, not ordering: production and clone have different explicit `anon`, `authenticated` or `service_role` EXECUTE grants. The three relation differences grant `anon` and/or `authenticated` all table privileges in the clone where production does not. The [guarded SQL candidate](../supabase/staging-reconciliation/post-head-privilege-reconciliation.sql) passed on the disposable copy, and a second run failed at its before-state guard without further change.
- The other 19 relation ACL differences are NULL versus `{postgres=arwdDxtm/postgres}`. All 19 local relations are owned by postgres; no non-owner grant is represented. One remaining function ACL differs only in ACL item order. A functional privilege check is still required on a **hosted** post-replay staging database before these can be waived there.
- Both hosted projects expose the same six extension names and the same seven platform event-trigger names. The local image adds `pg_net`, `pg_graphql` and two GraphQL watch triggers; its `regprocedure` display omits `extensions.` under the local search path. Hosted `issue_pg_graphql_access` has the same `CREATE EXTENSION` tags on both projects; the local image says `CREATE FUNCTION`. These are local platform effects, not proposed hosted DDL.
- The local column default becomes `extensions.gen_random_bytes` under a catalog-only search path, matching production. `mcp_internal.assign_production(...)` is byte-equal after removing SQL line comments. The `google_ads_build_due` view selects the same lateral fields and uses the same predicates; only the position of `b2.approved_spec` inside an internal projection changes with physical column order.
- A later read-only capture found **14** initial custom `storage.objects` policies, four buckets, zero object rows, and the postgres-owned `ensure_rls` trigger on staging. The [14-policy restore supplement](../supabase/staging-reconciliation/recovery-storage-policies.sql) and [trigger restore supplement](../supabase/staging-reconciliation/recovery-ensure-rls.sql) were applied to a fresh disposable local restore. All initial policies and the trigger were present before migration replay. Migrations then left **26** final Storage policies, matching the production comparison. The exact combined post-head SQL passed as postgres with **no ownership adjustment** on that clone. The hosted permission and Storage API paths remain untested.
- Hosted staging has `ensure_rls` with no event-tag filter, while production has `CREATE TABLE`, `CREATE TABLE AS`, `SELECT INTO`; both triggers are owned by postgres. The [guarded tag correction](../supabase/staging-reconciliation/post-head-ensure-rls-reconciliation.sql) is included in the exact combined candidate. Supabase's [CLI backup/restore guide](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) calls out custom Auth/Storage schema changes separately.

## Recovery gate before any hosted staging change

On 17 November, `supabase backups list --project-ref vmmertwoboqiazcsougw --output-format json` returned `backups: []` and `pitr_enabled: false` (`walg_enabled: true` did not list a restorable backup). The local logical checkpoint is private and restore-tested locally, but it is not a tested hosted rollback point or offsite copy. [Supabase's backup guide](https://supabase.com/docs/guides/platform/backups) says database backups exclude Storage object bytes; [the restore guide](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) requires separately handling custom Auth/Storage schema changes and migration history.

**Do not run the hosted sequence until one recovery route is actually tested:**

1. Obtain an authorized, isolated **hosted** restore target on the matching Supabase/Postgres platform, or a provider physical/PITR restore route with a tested restore to a separate project. No plan upgrade or extra project is assumed or authorized by this document.
2. Take a fresh, encrypted and access-controlled staging checkpoint immediately before the release. Include roles, application schema and data, Auth data, Storage bucket metadata and object bytes if nonempty, Vault material if nonempty, migration-history schema/data, custom Auth/Storage policies and triggers, `ensure_rls`, cron definitions and active states, extension inventory, and identity/row-count digests. Store it in an independently durable destination; record custodian, SHA-256 hashes and retention. Do not place passwords or token values in the packet.
3. Restore that checkpoint into the isolated hosted target. Verify all 277 history rows, client/Auth UUID digests, all nonempty table row counts or hashes, Storage object byte hashes, bucket settings, Vault recovery, **all 14 captured initial Storage policies**, `ensure_rls` ownership/tags, and cron schedule/command hashes. The read-only capture had zero Storage objects, but recheck immediately before restore and copy/verify bytes if that changes. Keep restored cron jobs inactive and external credentials/switches disabled. Verify a representative Auth login, Storage API access and data read without contacting live providers. If any component is unavailable, stop.
4. Rehearse the four PR #362 migration phases and the **exact combined post-head SQL** on that hosted disposable restore, including the postgres-owned event trigger. Compare production/staging schema definitions, effective grants, generated types and final history. Test a fail-closed changed-before-state and a controlled restore/forward-repair path. Record elapsed restore time and data-loss boundary. Only then propose a live staging window.
