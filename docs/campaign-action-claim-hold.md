# Generic campaign action claim hold

## Released behavior and reason

The runtime worker registered as `campaign_action_executor` refuses every generic campaign action **before it reads the registry or calls a claim RPC**, even if `CAMPAIGN_ACTIONS_ENABLED` and the client's campaign-action switch are on. An off runtime switch remains an ordinary idle success. An on switch produces a nonretryable job failure, a warning event, and a readiness hold reason. The client campaign action page shows the hold, disables its “Turn on” button, retains “Turn off,” and distinguishes a database-due action from one the runtime can execute. Existing exact-version decisions stay recorded; this change does not approve, reject, claim, retry, or alter one.

Migration 230 defines `claim_campaign_actions(p_limit integer)`. It has no action-key or handler-ownership parameter and claims any SQL-supported, due approval. The old worker read `campaign_action_executors` over PostgREST, compared support bits with local handlers, then called the claim RPC in another request. A registry support-bit promotion between those requests could make the SQL function claim an action with no handler. Postclaim rejection consumes an attempt and can abandon the exact human approval. Another registry read after claim would still be too late. The code-only containment is to make no generic claim.

The worker hold does not remove the service-role SQL function or prevent another service-role caller from invoking it directly. SQL cron can still enqueue sweep jobs when the due view says an approved action is ready. Those jobs fail visibly at the worker while this hold is active. Keep all external-effect switches off. The runtime's handler map still describes code present in the build; it is **not** an execution-ready capability while the hold exists. Dedicated queues and workers have separate gates and need their own source-specific review.

## Atomic SQL contract required to remove the hold

Implement and review a new claim RPC in a later migration after production recovery Q019 is closed. The old unfiltered RPC must be revoked from the service role before any generic worker is re-enabled. The replacement must, in **one transaction**:

1. Accept or derive an explicit runtime action-key allowlist and deployed runtime build identity. Reject an unknown or empty allowlist, stale deployed build, wrong executor module, unsupported registry row, and a key without a registered handler. Do not use a blanket `supported=true` scan as the claimant.
2. Lock the relevant registry rows against concurrent support updates while validating the selected candidate and taking the approval and execution locks. A support-bit change and a claim must have an unambiguous serial order. Recheck the key, support, module, client switch, current manifest, exact artifact hash, destination, scope, and execution status in that locked operation.
3. Require a current exact-version human Approval Inbox decision, including AAL2 where that action class requires it. The decision's source ID, version, snapshot and scope must match the claimed action; a pending, revoked, superseded or unsupported decision cannot be claimed.
4. Claim only rows owned by the supplied and validated runtime capability set, return exactly those rows, and record one idempotent execution and event per approval. Concurrent workers must not claim the same approval or consume an attempt for a rejected or unsupported key.
5. Keep provider-specific prewrite checks after claim and immediately before each external call. A timeout or unknown provider result must be reconciled from external IDs before retry; approval does not by itself authorize a duplicate write.

Release that migration and matching runtime together in dependency order. Run database concurrency tests that pause one transaction between registry validation and claim while another changes the support bit, plus wrong-key, wrong-build, stale-manifest, stale-Inbox-decision and duplicate-claim tests. Verify a deployed full runtime SHA and read-only production registry/claim-contract parity. Keep `CAMPAIGN_ACTIONS_ENABLED` and client switches off until an approved live pilot has exact external receipts. A later migration must also correct currently over-advertised support flags in campaign actions, proof destinations and profile fields; this runtime-only hold does not change those SQL claims.
